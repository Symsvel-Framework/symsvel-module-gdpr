## Traductions Svelte

Pour chaque scope Svelte du module (bo, app, front), placer les dictionnaires dans `<scope>/src/lib/translations/<lang>.ts` uniquement si des libellés sont nécessaires. Format obligatoire : `export default {"title":"Texte"} as const;` (objet JSON strict, pas de code TypeScript exécuté par Tooling). Clé publique : `<scope>.gdpr.<key>`. Tooling déploie les fichiers sous `<scope>/src/lib/translations/gdpr/<lang>.ts`, puis Languages persiste les clés après migrations. Le dossier initial est vide ; ne pas inventer de clés.

## Arbitrages mainteneur (27/11/2026)

`InactivityPolicy::activityReference()` utilise `last_login ?? created_at`, y compris pour les comptes historiques ; le préavis complet reste obligatoire. `PurgePolicy` choisit anonymize par défaut et refuse delete si un module actif exige la neutralisation. La clé Settings `gdpr.purge_locked` est calculée et non éditable ; le passage forcé vers anonymize devra être persisté afin de ne pas réactiver delete au déverrouillage. Ces classes pures ne déclenchent ni API ni cron. Voir ADR 0001 pour les garanties et limites.

## Déclaration d'anonymisation obligatoire

Un module actif dont les relations imposent de conserver l'identifiant User implémente `SymSvel\\Module\\Gdpr\\Retention\\AnonymizationRequirement` et enregistre son service Symfony avec le tag `symsvel.gdpr.anonymization_requirement` (autoconfiguration ou tag explicite). Le service doit retourner son identifiant canonique via `moduleId()` et ne doit pas lire les paramètres GDPR pendant la construction du registre. Le registre `AnonymizationRequirementRegistry` collecte les identifiants triés ; aucun contributeur = verrou inactif, un ou plusieurs = verrou actif. Toute déclaration invalide ou en double échoue explicitement. Le contrat de suppression des données métier par sujet reste distinct.

Le nom de clé est `gdpr.purge_locked`, équivalent de purge.locked dans la convention `module.parametre` (les clés à points imbriqués ne passent pas le qualificateur Settings). Le registre est câblé dans GdprBundle ; le provider projette le verrou dans Settings, dont la synchronisation persiste la valeur imposée et dont l'API refuse les écritures BO. Le registre représente les services du conteneur actif ; un réglage métier dynamique ne doit pas désarmer une contrainte de conservation encore applicable.

## Décision de consentement (27/11/2026)

`ConsentDecision` représente un choix explicite, positif ou négatif, pour un sujet de consentement identifié, sa révision et le scope App ou Front. Les dates sont normalisées en UTC ; une durée invalide est refusée. `ConsentPolicy::permits()` exige GDPR actif, une décision positive correspondant exactement au scope, au sujet et à la révision courante, et une date comprise dans l'intervalle [décision, expiration[. Une décision absente, périmée, future, négative ou d'une autre révision refuse tout chargement. Le retrait doit remplacer la décision courante par un refus ; le service pur ne sélectionne pas lui-même la dernière décision. `expiry()` calcule une échéance en mois calendaires, fin de mois plafonnée. Le stockage est décrit ci-dessous ; aucun cookie ni endpoint n'est encore implémenté. Le futur service de persistance devra fournir une décision authentique et courante, sans accepter un consentement arbitraire transmis par le navigateur. Tests unitaires dédiés ; raccordement Tracking, Settings, preuve et retrait à suivre.

## API de consentement navigateur (27/11/2026)

POST /apiopen/gdpr/{app|front}/consent/state lit le catalogue et la dernière sélection sans créer de ligne ni de jeton. PUT /apiopen/gdpr/{app|front}/consent accepte uniquement un objet JSON {version: null|string, choices: {subject: {revision: int, granted: bool}}}. Première décision : version null et choix explicites complets non vides ; la réponse data.credential contient le jeton signé à conserver seulement après la décision. Les appels suivants portent Authorization: Bearer <credential>, jamais le token de compte ni un cookie. La réponse data contient enabled, version, expires_at, complete et purposes. Tout retrait remplace la sélection, avec la version attendue ; 409 en cas de conflit, 401 jeton invalide, 403 origine/HTTPS refusée, 429 quota, 503 indisponible. Les réponses sont no-store. Le client doit rester sans traceur en cas d'erreur, recharger l'état après 409 et ne jamais journaliser le jeton. Le Back dev doit inclure le préfixe générique /apiopen dans CORS sans credentials. La migration Version20261127173001 ajoute une table de quota de création (une création/IP/seconde, toutes interfaces, HMAC d'IP, aucune IP brute) ; les remplacements avec version existante, y compris retrait, ne sont pas limités. Configurer trusted proxies et limitation réseau globale en production ; le quota local ne remplace pas une protection volumétrique. La commande `php bin/console symsvel:gdpr:cleanup-consents --env=prod` nettoie les choix expirés et les quotas anciens, même GDPR désactivé ; à planifier quotidiennement. Les tests SQLite couvrent API, stockage, refus, retrait, conflits et quotas. L'intégration navigateur, le rendu multilingue de la politique et la preuve historique complète restent à réaliser. Aucun loader ne doit être activé avant CT réseau.

## Arbitrage navigateur des écritures concurrentes et restauration du document

Chaque choix explicite crée un marqueur local distinct, avant tout PUT ou acquisition de verrou. Les navigateurs disposant de Web Locks sérialisent les écritures par scope avec acquisition non bloquante : une intention concurrente arrête les consommateurs, conserve son propre marqueur et demande une nouvelle confirmation, sans envoyer un second PUT concurrent. Une réponse ancienne ne peut effacer que les marqueurs déjà présents au début de sa propre intention, jamais un marqueur ultérieur ; tout changement observé invalide la réponse. Le marqueur historique .blocked reste reconnu. En HTTP local non sécurisé où Web Locks est absent, le client refuse de reprendre un marqueur pending d'un autre écrivain : un choix confirmé ou un abandon normal libère/convertit ses marqueurs ; après un crash brutal laissant un pending orphelin, une remise à zéro explicite des données du site peut être nécessaire. En contexte sécurisé, une nouvelle intention exclusive peut réconcilier les marqueurs orphelins. Les erreurs restent bloquantes. Aucun marqueur ni jeton n'est créé avant une décision utilisateur. pagehide invalide le permit et les réponses en vol ; une restauration BFCache relit l'état serveur avant tout nouveau permit. Tests unitaires de concurrence, compatibilité historique et insertion pendant commit ; Chromium deux onglets dans les deux scopes.

## Nettoyage des préavis

`symsvel:gdpr:process --cleanup-notices` inspecte les notices par pagination de clé, sans traiter les comptes. Ajouter `--execute` pour retirer uniquement des tentatives obsolètes, après relecture du sujet verrouillé (contrat optionnel `AccountRetentionInspector`), des Settings et de la tentative exacte. Les notices encore courantes restent conservées ; une tentative courante ambiguë ne devient jamais un préavis confirmé et n'est jamais libérée automatiquement. Une réservation obsolète mais récente (moins de 24 h) est conservée pour ne pas interférer avec un envoi potentiellement en cours ; les anciennes réservations obsolètes sont nettoyables. Le verrou local est partagé avec la commande de traitement. Sans inspecteur ou politique inactive, aucune suppression. La résolution manuelle d'un envoi courant ambigu exige une preuve indépendante de non-acceptation du transport ; aucune commande de validation forcée n'est exposée. Tests pagination, simulation, obsolescence, conservation des tentatives courantes et récentes.

## Page légale et exercice des droits

La route publique exacte `/privacy` est fournie par GDPR dans App/Front, via le mécanisme de routes Tooling. Runtime expose un lien sans dépendance à Tracking. Les textes `dataText`, `cookiesText`, `rightsText` et le contact `rightsEmail` sont personnalisables par scope/langue via Languages (`app.gdpr.*` et `front.gdpr.*`), avec publication et rebuild habituels. Svelte échappe les textes, conserve les sauts de ligne ; aucune injection HTML. Une adresse unique strictement validée crée un lien mailto avec objet seulement. Sans adresse valide, aucun lien de contact. La page reste publique indépendamment du réglage de consentement : les informations légales ne doivent pas disparaître lors de sa désactivation. Les droits sont exercés auprès du responsable, qui doit traiter et tracer les demandes hors de ce module ; aucun export automatique, dossier de demande BO ni effacement direct n'est revendiqué. Les textes fournis signalent explicitement leur configuration nécessaire. CT de personnalisation et de publication requis.

Alias de branche dev 1.0.x-dev aligné sur la recette Flex 1.0 ; aucune release stable créée.

Le lien mailto validé est explicitement externe au routeur SvelteKit ; le lint est neutralisé uniquement sur ce lien, sans modifier les règles de l'hôte.

## Correctif CT local : origine API native

Runtime réutilise `apiBaseUrl()` de l'hôte App/Front pendant l'hydratation navigateur, et transmet la même origine à ConsentPanel et au consommateur Tracking. L'URL explicite `PUBLIC_API_URL` reste prioritaire ; le fallback natif est utilisé en local. Aucun accès à `window` au prérendu. Le client garde la validation stricte d'URL, le serveur garde la validation exacte des origines Setup et le refus par défaut. La QA Playwright exécute les scénarios de consentement sans `PUBLIC_API_URL`, puis le scénario consommateur avec une URL explicite. Front doit être mis à jour avec le helper commun avant le nouveau GDPR.

La garde de prérendu utilise `typeof window === 'undefined'`, comme les helpers natifs, sans import `$app/environment` non résolu par le contrôle TypeScript des hôtes. La même QA de build statique et de consentement navigateur couvre ce raccordement.
